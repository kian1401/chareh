# 🚀 راهنمای استقرار چاره — از گیت‌هاب رایگان تا تولید ایرانی

دو مسیر داریم که **موازی** جلو می‌روند:

| مسیر | هدف | هزینه | آماده برای |
|---|---|---|---|
| **A. رایگان** (الان) | نسخه‌برداری کد، بیلد خودکار APK، گزارش باگ همکاران | ۰ تومان | تست آلفا با همکاران |
| **B. تجاری ایرانی** | بک‌اند واقعی، در سیری مراجعین، درگاه و پیامک | ≈ ۱ تا ۳ میلم تومان/ماه | راه‌اندازی عمومی |

## 🅰️ مسیر رایگان (امروز)

### ۱) گیت‌هاب — سه راه دارید

⚠️ در این گفتگو، گیت‌هاب «متصل» نیست، پس پوش را خود شما انجام می‌دهید؛ من همه فایل‌ها را آماده کرده‌ام (`git log` را ریپو دارد).

**راه ۱: از این محیط با توکن شخصی (PAT)**
```bash
# ۱. در گیت‌هاب: New repository → نام: chareh → Private یا Public
# ۲. Settings قدیمی: github.com/settings/tokens → Generate new token (classic) → اسکوپ repo
# ۳. اینجا اجرا کنید:
cd /home/user/chareh
git remote add origin https://<TOKEN>@github.com/<USER>/chareh.git
git branch -M main
git push -u origin main
```

**راه ۲: روی لپ‌تاپ خودتان — دانلود ZIP فایل `chareh.tar.gz` از فضای کاری، بعد:**
```bash
git init && git add -A && git commit -m "v1.0.0"
git branch -M main
git remote add origin git@github.com:<USER>/chareh.git
git push -u origin main
```

**راه ۳: ترمینال `gh`**
```bash
gh auth login
gh repo create chareh --private --source=. --push
```

### ۲) بیلد خودکار روی هر push — آماده‌ست ✅
فایل `.github/workflows/apk.yml` که گذاشتم:
- دو APK (مشتری + متخصص) + وب را می‌سازد
- APKها را به‌صورت **Artifact** و با تگ `v*` در **Releases** می‌گذارد
- همکاران مستقیم از تب Actions یا Releases دانلود می‌کنند — بدون نیاز به فلاتر

### ۳) رندر — وب‌اپ رایگان (ریفایل `render.yaml` ریشه ریپو)
رندر این Blueprint را**خودکار** می‌شناسد:
1. render.com → ثبت‌نام با گیت‌هاب
2. **New → Blueprint** → ریپوی `chareh` را انتخاب کنید
3. تمام! وب‌اپ + صفحه دانلود APK با دامنه `.onrender.com` بالا می‌آیند

> ⚠️ **محدودیت رندر رایگان (۱۴۰۵/۲۰۲۶):** وب‌استاتیک نامحدود و عالی است ولی **وب‌سرویس (API) فری**
> بعد از ~۱۵ دقیقه بی‌استفاده می‌خوابد (بالا آمدنش ~۳۰ ثانیه طول می‌کشد) و دیتابیس رایگان Postgres
> فقط ۳۰ روز ماندگار است. برای دمو بسیار خوب است، برای تولید **نه** ← مسیر B.

### ۴) چرخه تست همکاران 🔁
1. همکار: APK را از Releases یا صفحه `/download/` نصب می‌کند
2. باگ می‌بیند ← در گیت‌هاب → **Issues → New Issue** ← فرم فارسی «گزارش ایراد» سوالات می‌پرسد (نقش، دستگاه، مراحل، شدت) — قالب دستی نیست
3. شما: Issue را assign/لیبل → من در Arena فیکس می‌کنم → push → CI نسخه جدید می‌سازد
4. همکار: آپدیت می‌کند (بعداً: بیلد OTA بین‌نسخه خودکار)

### 🎯 سناریوی تست آلفا (به همکاران بدهید)
```
۱. اپ مشتری → ورود دمو → رزرو «سرویس کولر آبی» → ثبت تراکنش (دمو) → پیگیری سفارش
۲. اپ متخصص (گوشی دیگر) → «درخواست‌ها» → پذیرفتن → «در مسیر» → «شروع» → اتمام
۳. اپ مشتری → تایم‌لاین به‌روز شد؟ امتیاز ⭐ + تسویه کیف پول + %
۴. ادمین (وب) → گزارش‌ها → ساخت منطقه جدیده
۵. باگی؟ مشکل/تأخیر؟ هر چیز ناراحت‌کننده؟ ← Issue با فیلم📹
```

## ⚠️ نکته فنی مهم قبل از تست همکاران
> دیتای فعلی اپ **لوکالِ همان گوشی** است؛ یعنی رزرو معاون جانمایی در گوشی متخصص دیده **نمی‌شود**.
> برای تست واقعی نقش‌ها پشت هم، باید **یک بک‌اند مشترک** به جای دیتای Mock بیاید.
> آبی‌حشره می‌خواهم معماری RepoHub انتخابی دارد — فقط یک RemoteHub می‌سازم.
> این همان سوال سوم در پاسخ بعدی است.
